# 🤝 Участие в разработке

Спасибо за вклад в проект! Эта страница описывает, как вносить изменения.

## Перед началом

1. Настройте окружение — см. [Установка](../getting-started/installation.md).
2. Убедитесь, что тесты проходят: `npm test`.

## Процесс внесения изменений

1. **Создайте ветку** от актуального `main` — см. [git-workflow](./git-workflow.md).
2. **Сделайте изменения** небольшими и сфокусированными.
3. **Соблюдайте стиль кода** — см. [code-style](./code-style.md).
4. **Покройте код тестами** — см. [тестирование](../guides/testing.md).
5. **Прогоните тесты:** `npm test`.
6. **Закоммитьте** по соглашению о сообщениях (ниже).
7. **Откройте Pull Request** в `main` с понятным описанием.

## Сообщения коммитов

Используется формат [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
<тип>: <краткое описание>

[необязательное тело]
```

Типы:

| Тип | Когда использовать |
|-----|--------------------|
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Изменения только в документации |
| `test` | Добавление/изменение тестов |
| `refactor` | Рефакторинг без смены поведения |
| `chore` | Рутина (зависимости, конфиги) |

Примеры:

```
feat: добавить пагинацию в api.getUser
fix: сбрасывать таймер в fetchWithTimeout при ошибке
docs: описать модуль queue в справочнике API
```

## Требования к Pull Request

- [ ] Тесты проходят локально (`npm test`)
- [ ] Новый код покрыт тестами
- [ ] Соблюдён стиль кода
- [ ] Описание PR объясняет, **что** и **зачем**
- [ ] Нет секретов и лишних файлов в диффе

## Чего не делать

- Не коммитьте `node_modules/`, секреты, временные файлы.
- Не добавляйте нестабильные (flaky) тесты — см. предупреждение в [тестировании](../guides/testing.md).
- Не смешивайте несвязанные изменения в одном PR.
