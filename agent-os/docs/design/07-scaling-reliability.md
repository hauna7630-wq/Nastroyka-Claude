# 07 — Scaling & Reliability Strategy

## Текущий масштаб
Один RU-хост (2 vCPU / 4GB): compose-стек (Caddy, Postgres, Redis, agentos,
teamly). 7+ агентов, conc=4 параллельных run'а — запас по CPU кратный
(узкое место — латентность LLM, не хост).

## Надёжность (реализовано)
- Очередь: ретраи с бюджетом на Run, DLQ + ручной requeue из Админки.
- Идемпотентность: createRun upsert по id; child id детерминированы;
  Step upsert по (runId,index); ответ чата — unique(runId,role).
- Рестарты: миграции на старте; lazy-backfill чинит «потерянные» ответы;
  UI-поллинг не сдаётся, пока run не терминален.
- Деплой: CI собирает образы → SSH → pull/up → авто-сид → E2E (живой чат-раунд,
  маркеры UI, проверка «закрыл вкладку-вернулся») — регрессия видна в пайплайне.
- Фолбэк деплоя при очередях GitHub-раннеров: локальная сборка на хосте
  (задокументирована в HANDOFF.md §3).

## Пути горизонтального роста (спроектировано)
1. Разнести control plane и worker: уже разделены кодом (`startWorker` /
   `createControlPlaneServer`), шина уже кросс-процессная (Redis) — нужен
   только второй контейнер с тем же образом и ENV-флагом роли.
2. Несколько воркеров: BullMQ это поддерживает из коробки; инварианты
   идемпотентности уже выдерживают конкурентную доставку.
3. Postgres: managed-инстанс + реплика на чтение; шардинг по Org при
   необходимости.
4. Очередь → NATS/Kafka только при многосервисной топологии (сейчас оверкилл).

## Восстановление после катастроф (частично)
Есть: версионированные образы в GHCR, redeploy за ~6 мин, идемпотентный сид.
Нужно (задача): pg_dump cron на внешнее хранилище + ротация засвеченных
секретов; релей US — второй экземпляр Caddy поднимаетcя из HANDOFF за минуты.
