# 11 — Codebase Integration System (designed)

Слой, позволяющий агентам безопасно работать над реальными репозиториями
(Next.js/React/TS). Статус: **спроектировано** (кода нет; ниже — архитектура и
явные допущения). Никаких прямых записей в код — только через цикл с проверкой.

## Допущения
- Агенты исполняются в песочнице (есть `code_exec` subprocess/docker-адаптер) —
  переиспользуется для AST-парсинга и сборки в изоляции.
- Целевой репозиторий монтируется read-only; запись — только в рабочую копию
  ветки, патч применяется через git, не правкой файлов «вслепую».
- Модель не имеет прямого доступа к диску продакшена — оперирует представлением
  (дерево, AST, граф зависимостей) и предлагает diff.

## Возможности (порт `CodebaseConnector`)
`readTree()`, `readFile(path)`, `parse(path) → AST`, `dependencyGraph()`,
`componentMap()` (React-компоненты: пропсы, импорты, где используется),
`proposeDiff(plan) → unified diff`, `applyPatch(diff)` (в ветку), `verify()`.

## Конвейер
1. **Ingestion** — обход дерева, фильтр по .ts/.tsx/.css; игнор node_modules.
2. **AST-парсинг** — TypeScript Compiler API / SWC; извлечение экспортов,
   JSX-структуры, импортов.
3. **Граф зависимостей** — рёбра import/использование; обнаружение циклов.
4. **Семантическая карта UI** — компонент → роль (страница/лейаут/виджет/
   примитив), связь с design-system (см. doc 12, ingestion 21st.dev как внешний
   датасет).
5. **Генерация изменения** — агент-инженер предлагает план (что и зачем).
6. **Слой валидации** — типы (tsc), линт, тесты, бюджет производительности.
7. **Безопасное применение** — патч в отдельную ветку, PR-артефакт.

## Модель безопасности: PLAN → REVIEW → DIFF → APPLY → VERIFY
- **PLAN**: оркестратор декомпозирует задачу (уже есть); инженер описывает
  намерение текстом.
- **REVIEW**: ревьюер (уже есть раунд ревью) проверяет план на риски ДО кода.
- **DIFF**: генерируется unified diff; прямые записи запрещены (порт отдаёт diff,
  не пишет файл).
- **APPLY**: `git apply` в ветку `agent/<task>`; коммит с трассировкой задачи.
- **VERIFY**: tsc + тесты + бюджет FPS (doc 12); провал → diff отклонён,
  фаза `failed`, ничего не влито.
- Откат/компенсация: каждый APPLY — отдельный коммит; rollback = revert ветки.

## Наблюдаемость (новые события шины)
`CodebaseChangeProposed`, `CodebasePatchApplied`, `CodebaseVerifyFailed` —
ложатся в существующую модель событий (doc 05) и трекер diff-истории (Admin).

## Риски / failure modes
- Неверный AST на экзотическом синтаксисе → парсер возвращает ошибку, задача
  не падает молча (контракт честности как у файлового парсера, doc 11≈doc-1).
- Большой репозиторий → инкрементальный индекс + кэш графа в Postgres/pgvector
  (semantic memory codebase-mapping, doc 13 мастера).
- Конфликт патча → VERIFY ловит, фаза `failed`, предлагается ребейз.
