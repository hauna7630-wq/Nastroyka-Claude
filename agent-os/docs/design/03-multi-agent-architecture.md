# 03 — Multi-Agent Architecture

## Роли (реализовано)
`AgentType`: orchestrator / researcher / analyst / writer / coder / reviewer.
Специализация обеспечивается тремя слоями: (1) экспертный системный промпт
(PromptVersion, версионируется, откат = выбор старой версии); (2) per-agent
allowlist инструментов; (3) маршрутизация подзадач по типу
(`findAgentByType`).

## Координация (реализовано)
Оркестратор — контролёр, не исполнитель: принимает задачу → планирует
(JSON-план от модели, валидация + topo-sort, защита от циклов) → назначает
типизированным агентам → контролирует статусы детей → агрегирует → запускает
ревью и доработку. Личный чат с оркестратором — прямой диалог (минует
планирование): персона отвечает сама.

## Коллективное мышление (реализовано)
Цикл: план → работа → ревью (Revisa, вердикт «Готово к выпуску»/«Нужны
доработки») → один revision-раунд (синтез-агент дорабатывает по критике).
Ответ — атрибутированный отчёт: синтез + «Вклад участников» + секция ревью.
Спроектировано (следующая итерация): многораундовые дебаты с лимитом раундов
и протоколом несогласия (агент обязан указать, с чем не согласен и почему).

## Идемпотентность ре-исполнения (реализовано)
Child id = `parent::subtaskId` (`::review`, `::rev1`); `createRun` — upsert:
ретрай оркестрации не пересоздаёт завершённых детей.

## Деградации (реализовано)
Невалидный план → fallback одиночного агента (audit `plan_fallback`); сбой
ревью — нефатален; пустой вывод модели — fail с ретраем; нет агента типа —
честная ошибка «наймите во вкладке Команда».

## Найм (реализовано)
Agent Factory (`POST /agents`) + каталог команд (10 шаблонов, идемпотентный
найм по имени, audit `team.hired`).
