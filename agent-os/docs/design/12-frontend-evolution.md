# 12 — Frontend Evolution Engine (designed)

Система непрерывной автономной эволюции UI: «живая» интерактивная среда с
жёсткими гарантиями производительности. Статус: **спроектировано**. Честно: я НЕ
просматривал 21st.dev — он трактуется как внешний датасет компонентов, который
ингестится пайплайном (ниже), без претензии на браузинг.

## Целевой опыт (2026 UI)
Анимированные среды (вода/ветер/листва), пространственные переходы,
motion-first микровзаимодействия, scroll-driven слои. ЖЁСТКОЕ ПРАВИЛО: ни одна
фича не включается, если роняет UX ниже порога производительности.

## Архитектура рендера
- **Абстракция WebGL/Canvas**: единый порт `Renderer` (как у нас порты в ядре);
  реализации Canvas2D (есть, офис) и WebGL (designed для тяжёлых сцен) — выбор
  по возможностям устройства и бюджету.
- **Планировщик кадров**: один `requestAnimationFrame`, дельта-тайм, пропуск
  тяжёлых слоёв при просадке (adaptive quality).
- **LOD**: тиры детализации (близко/далеко, мало/много объектов); деградация
  спрайтов и эффектов вместо падения FPS.
- **GPU-fallback**: при отсутствии WebGL/слабом GPU — Canvas2D-путь с
  отключёнными шейдерными эффектами.
- **Worker-offload**: тяжёлые вычисления (layout, частицы) — в Web Worker;
  главный поток только рисует.

## Performance-first (жёсткие требования)
- Базовый **60 FPS** (минимум 50 на 2-ядре с ≤12 агентами — измеримо);
- адаптивное качество (снижение эффектов при падении кадра);
- ленивая загрузка визуальных систем (эффект включается при появлении в кадре);
- частичная гидрация (Next.js) для статичных зон;
- стриминг ассетов; запрет синхронных тяжёлых операций в rAF.

## Ingestion компонентов (внешний датасет, напр. 21st.dev)
Пайплайн «знаниевого слоя» (НЕ браузинг сайта):
1. **Импорт** — компоненты/паттерны поступают как датасет (экспорт/JSON/код).
2. **Нормализация** — к внутренней модели design-system (примитив, пропсы,
   варианты, токены, motion-определения).
3. **Индексация** — в pgvector (semantic memory, doc 13 мастера): поиск
   «нужен компонент для X».
4. **Связывание** — компонент ↔ узлы codebase (doc 11 componentMap) ↔ агенты.
5. **Переиспользование** — агент-инженер предлагает применить компонент через
   безопасный цикл PLAN→REVIEW→DIFF→APPLY→VERIFY (doc 11).

## Безопасный цикл автоулучшения UI
1. Анализ состояния UI → 2. Поиск возможностей улучшения → 3. План улучшения →
4. **Симуляция влияния на производительность** (оценка FPS/памяти ДО применения)
→ 5. Предложение diff → 6. Проверка бюджета (VERIFY роняет фичу при просадке) →
7. Применение → 8. Мониторинг регрессий (визуальный + FPS).

## Версионирование UI-ассетов (требование v16+)
Паки спрайтов версионируются (vNN — у нас уже бейдж версии в шапке как маркер
свежести). Designed: пост-деплой UI Coordinator инициирует
**screen-capture-валидацию** → визуальный diff против предыдущей версии →
acceptance-отчёт (стабильность лейаута, корректность анимаций, стабильность FPS).
Версия не принимается без визуальной верификации.
Честное ограничение: sandbox не рендерит canvas — визуальную приёмку сейчас
делает пользователь по скриншотам; автоматический screen-capture — designed-слой
(headless-браузер на US-боксе как раннер визуальных проверок).
